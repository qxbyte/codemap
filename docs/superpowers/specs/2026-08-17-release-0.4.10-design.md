# CodeMap 0.4.10 Release Hardening Design

## Context

CodeMap contains `codemap-core` plus 20 plugin distributions. The current source
versions are `0.4.9` for core and 19 lockstep plugins, and `0.2.2` for
`codemap-semantic-index`. PyPI currently exposes `0.4.6` for the lockstep group
and `0.2.2` for semantic index because commits `0.4.7` through `0.4.9` were not
tagged.

The release audit found three concrete reliability gaps:

1. Nineteen plugin distributions require `codemap-core>=0.3.0,<0.4`, so pip
   cannot install them alongside any `codemap-core 0.4.x` release.
2. Plugin package `__version__` values and registered component `version`
   values remain at historical `0.1.0` or `0.2.0` literals instead of matching
   the installed distribution.
3. The main CI workflow runs core tests but does not execute each plugin's own
   test suite or validate every distribution before a release tag.

Current functional behavior is otherwise healthy: 653 plugin tests and 297 core
tests pass on Python 3.12, with one expected core skip and 88.38% core coverage.

## Goals

- Publish an installable, internally consistent 21-package release.
- Release `codemap-core` and the 19 lockstep plugins as `0.4.10`.
- Release `codemap-semantic-index` independently as `0.2.3` in the same publish
  matrix run.
- Make package compatibility, version consistency, plugin tests, builds, and
  artifact rendering verifiable before a tag is pushed.
- Keep parser, recall, persistence, and CLI behavior unchanged except that
  reported plugin/component versions become accurate.

## Non-goals

- No parser feature work, retrieval ranking changes, schema migrations, or
  performance tuning without a failing benchmark or behavioral test.
- No dependency refresh unrelated to release correctness.
- No redesign of the existing GitHub OIDC Trusted Publishing workflow.

## Package and Version Contract

The root distribution and all plugin `pyproject.toml` files remain the source of
truth for distribution versions.

- `codemap-core` and every plugin except `codemap-semantic-index` use `0.4.10`.
- `codemap-semantic-index` uses `0.2.3`.
- The 19 lockstep plugins require `codemap-core>=0.4.0,<0.5`.
- `codemap-semantic-index` keeps `codemap-core>=0.4.1` and
  `codemap-aimemory>=0.4.1` because its version line is independent.
- Every import package exposes `__version__` through `importlib.metadata` with
  `0.0.0.dev0` only as the source-tree fallback when distribution metadata is
  unavailable.
- Registered indexers, resolvers, bridges, and emitters use their owning
  package's `__version__` rather than duplicated literals. This makes `doctor`
  and index manifests accurately reflect the installed implementation and
  allows incremental index state to notice plugin upgrades.

A release-contract test discovers package metadata rather than maintaining a
second hand-written package list. It asserts:

- the repository package set equals the publish workflow matrix;
- package names and versions are unique and follow the two version groups;
- every plugin's core requirement accepts the release's core version;
- every registered component obtains its version from package metadata rather
  than a stale literal.

## CI and Artifact Validation

The existing core quality matrix remains responsible for macOS/Linux and Python
3.11/3.12/3.13 coverage.

A new Ubuntu plugin/package matrix covers all 21 distributions. Plugin rows
install the local core and the selected plugin with its development extras, then
run that plugin's tests from its own directory so the repeated top-level `tests`
package names cannot collide. Every row builds both wheel and sdist and runs
`twine check` on the artifacts. The core row builds and validates core artifacts;
its behavior tests remain in the existing quality matrix.

The final local preflight repeats the same checks and additionally creates a
clean environment that installs the exact built wheel set together. It verifies
the `codemap` CLI, plugin discovery, and reported distribution versions without
using editable installs.

## Lint and Documentation Hygiene

Current Ruff reports two formatting changes in documentation code blocks and
nine `PLR0917` findings. The project already ignores `PLR0913` because public
APIs and Typer commands legitimately accept multiple arguments. `PLR0917` is
therefore ignored next to it with the same explicit rationale instead of
refactoring stable call signatures solely for a newly introduced lint rule.

Ruff formatting is applied only to the two reported documentation files.
README, installation examples, and changelogs are updated to the release
versions and the complete 21-package matrix. Historical changelog entries are
not rewritten.

## Error Handling and Release Safety

- Any failing contract, test, lint, type, import-boundary, build, `twine`, or
  clean-install check blocks version publication.
- The release commit uses the repository's required Codex/user co-author
  trailers.
- The branch is pushed before publication so GitHub CI can validate the exact
  commit. The final `v0.4.10` tag is created only from that validated commit.
- Pushing `v0.4.10` triggers the existing production PyPI workflow. Its
  `skip-existing` behavior safely ignores older published versions while
  uploading the new `0.4.10` and `0.2.3` artifacts.
- The task is complete only after the workflow succeeds and the PyPI JSON APIs
  report all expected versions.

## Acceptance Criteria

1. All 653 existing plugin tests pass independently.
2. The core test suite passes with at least 80% coverage.
3. Ruff format/check, strict mypy, and import-linter pass.
4. The release-contract test passes for all 21 packages.
5. All 21 wheels and sdists pass `twine check`.
6. A clean environment installs the complete built artifact set and reports
   core/plugin versions `0.4.10`, with semantic index `0.2.3`.
7. GitHub CI passes on the release commit.
8. The `v0.4.10` publish workflow succeeds.
9. PyPI reports the expected version for every distribution in the publish
   matrix.
